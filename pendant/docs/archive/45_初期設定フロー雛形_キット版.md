# 45. 初期設定フロー（雛形）— キット版の書込み・鍵の受け渡し・初回ペアリング

Status: **DRAFT（2026-10-14、issue #6）。** フロー図だけで、実装も決定もしない。決めることは §5 に残した。前提: 24（キット構成）、31（LESC + OOB の案）、35（OTA・署名鍵）。

## 1. 前提（確認済み）

- XIAO nRF54L15 の USB-C は **SAMD11 の CMSIS-DAP / UART ブリッジ**につながる（回路図）。**nRF54L15 自身は USB に出ない**ので、「USB 書込み」は SWD 書込み（CMSIS-DAP）で、このリポジトリで使っている `pyocd load` と同じ経路。**スマホ（Android / iOS）が直接 SWD 書込みできる保証はない**（WebUSB 版の CMSIS-DAP 実装はあるが、本調査では未確認）。
- 書込みは「電池を付けない状態」で行う（24: 電池装着の前に USB を終える。25 / 36: USB と 5V ピンの電池を同時につながない）。
- ペアリングは LESC + OOB が案（31 §3）。OOB の鍵と保存データの鍵は**書込み側がデバイスごとに作り、デバイスと書込み側の両方に渡す**。

## 2. 提案のフロー（PC 書込み版）

```text
 [購入者の PC: lifeOS 書込みツール]                [XIAO（電池なし、USB-C）]          [スマホ（lifeOS アプリ）]
   │ 1. デバイスごとの秘密を生成                       │                                   │
   │    (OOB 鍵 / 保存データ鍵 / デバイス ID)          │                                   │
   │ 2. FW（署名済み）+ 秘密の領域を 1 つの hex にして ─▶ 3. SWD で書込み（pyocd 相当）       │
   │    storage パーティション（36 KB）に秘密を置く    │    MCUboot → アプリ起動              │
   │ 4. QR コードを表示（デバイス ID + OOB 鍵）        │                                   │
   │                                                   │  5. 初回起動: 秘密を検出 →          │
   │                                                   │     「ペアリング窓」を開く          │
   │                                                   │     （広告はフラグのみ、31 §4）      │
   │ 6. USB を抜く → XIAO を carrier へ → 電池を装着    │                                   │
   │                                                   │ ◀─ 7. QR を読む ─ 8. LESC + OOB でペアリング
   │                                                   │ ◀─ 9. TIME（時刻設定。timefix レコードが残る）
   │                                                   │ ◀─ 10. 最初の SYNC（INFO で ring 状態を確認）
   │                                                   │  11. ペアリング窓を閉じる（bond 済み機器だけ）
```

- **秘密の置き場所**: `storage` パーティション（0xB0000、36 KB、現在未使用。35 §2）。**書込みツールが hex に含める**ので、書込み時に UART 通信も要らない（pyocd だけで済む）。
- **デバイス側の状態**: `UNPROVISIONED`（秘密なし。録音しない、広告しない）→ `PROVISIONED`（秘密あり、未ペアリング。ペアリング窓が開く）→ `PAIRED`（bond 済み。Filter Accept List のみ接続可）。**窓は初回の書込み直後だけ開く**（31 §4: 物理ボタンを増やさない）。
- **紛失・再ペアリング**: 再書込み（鍵の作り直し）。既存の bond は無効になる（31 §3）。
- **署名鍵**（35 §7 #1）: 書込むイメージは開発用鍵のまま配布できない。署名鍵の持ち主（メーカーの鍵で全員のイメージに署名する案が有力）が決まる必要がある。

## 3. 変形: スマホ書込み版

- スマホが SWD 書込みを行うのは**未検証で実現性が不明**（上記）。成立するなら、スマホアプリが鍵を作り、PC 版の 1〜4 を代行する。成立しないなら PC 版のみ。
- **BLE DFU（35 の MCUboot + MCUmgr）だけでアプリを入れる案**は、MCUboot が最初に入っている必要があり、**初回の書込みは SWD が要る**。購入者に MCUboot まで書かせる（または工場で MCUboot だけ書いて同梱する）かの選択が残る。

## 4. 初回の同期の注意（実機で確認した点）

- 録音は書込み直後から始まる設定のまま（`AUTO_RECORD`）。**ペアリング前の録音を保存するか破棄するか**を決める（保存データは鍵で暗号化する案、31 §5。鍵がなければ保存しない案が安全）。
- 時刻はペアリング後の TIME（`0x03`）で入る。それまでの記録は RTC 無効フラグ付きで、後の timefix から UTC に直せる（28、33 の PORF / VLF の扱い）。**電池を付けるより前に時刻を入れる手段はない**（RTC の電源が電池側のため）。

## 5. 決めてほしいこと（issue #6、24 / 26 / 31 と共通）

1. **書込み手段は PC 経由でよいか**（スマホ書込みは未検証のため。PC 経由なら QR でスマホに鍵を渡す）。
2. **初回の鍵・秘密の置き場所を `storage` パーティションにしてよいか**（暗号化と KMU の使用は #26 の決定に依存）。
3. **ペアリング前の録音の扱い**（暗号鍵が無い間は保存しない案を推奨）。
4. **MCUboot を誰が書くか**（購入者の書込みツールが MCUboot + アプリを一緒に書く案を推奨）。
