# セキュリティ仕様: 脅威モデル・ペアリング・鍵・暗号化・デバッグ保護

首から下げて常時録音するデバイスなので、機能そのものが「盗聴器と隣り合わせ」にある。守る対象は 2 つ。

1. **所有者**: 会話の録音が第三者に盗まれない。デバイスを追跡・特定されない。
2. **周囲の人**: デバイスが他人を無断で録る道具として悪用・誤認されにくい。

法的な判断はこのファイルでは行わない（論点の洗い出しまで）。

このファイルが持つもの: 脅威モデル、ペアリング、広告とプライバシー、保存データの暗号化、鍵と初期化、署名鍵、デバッグ保護、誤用・誤認対策。

他のファイルが持つもの:
- OTA、MCUboot、パーティション、ウォッチドッグ、時刻: [firmware.md](./firmware.md)
- レコード形式、BLE 同期: [formats.md](./formats.md)
- 赤 / 黒の終端表示: [terminal-indicator.md](./terminal-indicator.md)
- 技適・SIG・CE・FCC・EN 18031: [plan/compliance.md](../plan/compliance.md)

確度の凡例: **確定** = 決定済み。**方針** = 向きは決まっているが数値・手順は未定。**仮置き** = 実測で決める。

## §1 要約

| 項目 | 内容 | 確度 |
|---|---|---|
| ペアリング | LE Secure Connections（LESC）+ OOB。Just Works は使わない | 確定 |
| 広告 | 機器名・サービス UUID・メーカーデータを載せない。RPA を有効にする。ボンド済みのスマホが IRK で見つける | 確定 |

## §2 脅威モデル

| 攻撃者 | 守る | 理由・対策 | 守らない |
|---|---|---|---|
| 通りすがりの追跡者（広告を拾う） | 一部 | RPA で広告アドレスを定期的に変える。広告に名前・UUID・固有データを載せない。広告は短時間・低頻度 | 電波そのものの指紋、「広告を出していること」の秘匿 |
| 近距離の盗聴者（接続・同期中の傍受） | ○ | LESC で暗号化。OOB で中間者攻撃を防ぐ（Just Works は中間者に弱い） | 接続中のトラフィック量・時間の推定 |
| 端末の紛失・盗難（保存データの読み出し） | 条件付き | レコードを暗号化して保存（§5）。SWD で鍵を読み出せる間（APPROTECT OFF）は、外付け NAND を抜いて読む攻撃にだけ効く | APPROTECT OFF のまま鍵が読み出せる構成。物理的に強い攻撃者（チップ解析） |
| 悪意ある所有者 | 守らない | 所有者は自分の装置の録音を取り出せる前提。周囲の人への告知は §9 | — |
| 悪意あるスマホアプリ・ペアリング済み機器 | 守らない | ペアリングした機器は信頼する | — |

「守る」の範囲は BLE の仕様で取れる範囲に限る（広告ペイロードや送信間隔の特徴による個体推定、電波の指紋は取れない）。

守る価値が高いもの: OTA 署名鍵に関わる秘密、ペアリング・identity の資格情報、ユーザー固有の metadata、保存した音声。ファームウェアそのものの IP は優先度が低い。

3 つの保護を混同しない:

| 保護 | 守るもの |
|---|---|
| 署名付き OTA（MCUboot） | ファームウェアの真正性（§7） |
| APPROTECT 等 | デバッガによる物理アクセス（§8） |
| 保存データの暗号化 | 保存した音声の機密性（§5） |

MCU の debug lock だけでは、外付け NAND に保存した音声を物理攻撃から守れない。

## §3 ペアリング

画面が無いので Numeric Comparison と Passkey は使えない。

| 方式 | 中間者攻撃 | 判断 |
|---|---|---|
| Just Works | 弱い（認証なし） | 使わない |
| LESC + Passkey | 強い | 使えない（画面なし） |
| **LESC + OOB** | 強い | **採用（確定）** |

- OOB の鍵の作り方と、スマホへの渡し方は §6（未確定）。
- ペアリングモードに入れるのは **初期化の直後の初回のみ**（物理ボタンを増やさない）。以降は窓を開けない（方針）。
- 紛失・買い替え時の再ペアリングの手順は未確定（末尾の「未確定」に記載）。
- 開発ビルド（Phase 0）の GATT は無認証で開いている（`CONFIG_PENDANT_BLE_SECURE=n`）。机上の試験用で、配布してはならない。`PENDANT_BLE_SECURE=y` で全 characteristic に暗号化を要求する。製品ビルドでは y にする。

## §4 広告とプライバシー

- `CONFIG_BT_PRIVACY=y`（RPA）を有効にする。回転周期は Zephyr の既定（900 s、要確認）から始める。
- 広告に載せるのは **フラグだけ**。機器名・サービス UUID・メーカーデータは載せない（確定）。ボンド済みのスマホが IRK で RPA を解決して見つける。開発ビルドの `CONFIG_BT_DEVICE_NAME` は製品では載せない。
- 広告は短時間・低頻度（README の想定は約 2 時間ごと）。露出を減らす方向。同期の信頼性（スマホが拾える時間）とのバランスは BLE 同期の実装（#7）で見る。
- 接続は Filter Accept List でボンド済みの機器に限る（方針）。
- 未確認: Zephyr / SoftDevice Controller で、RPA と Filter Accept List を同時に使うときの広告方式（指向広告にするか）。

## §5 保存データの暗号化（確定: する）

| 項目 | 内容 |
|---|---|
| 方式 | AES-128-GCM（CRACEN 経由の PSA） |
| 単位 | 1 レコードの payload |
| 認証データ（AAD） | レコードの header（40 B） |
| nonce | `boot(4) + seq(4) + 0(4)`（12 B）。(boot, seq) が一意なら重複しない |
| タグ | payload の末尾に 16 B（長さは 4 の倍数のまま） |
| CRC | 暗号文に対してそのままかける |
| レコード形式への影響 | `flags` に ENCRYPTED を 1 ビット追加（フラグ 0 なら暗号化なし）。形式の定義は [formats.md](./formats.md)。ring は中身を見ないので変更不要 |

実測（XIAO nRF54L15、128 MHz、CRACEN、32,000 B、header 40 B を AAD）:

| 項目 | 値 |
|---|---:|
| 暗号化 | 0.47 ms（約 68 MB/s） |
| 復号と検証 | 0.47 ms |
| 8 s の録音に対する時間の割合 | 約 0.006 % |
| 参考: ADPCM 符号化（同じ 8 s） | 約 43 ms |

- ハードウェア暗号エンジンが使われ、CPU の負荷は無視できる。電力は ADPCM の約 1 % 以下（CRACEN の稼働電流は未測定。Phase 1 で測る）。ベンチは `fw/src/crypto_bench.c`（`PENDANT_CRYPTO_BENCH`）。
- スマホ側が復号する。BLE では暗号文のまま送り（端末間の暗号化）、スマホが鍵で復号する。ASR や欠落の扱いには影響しない。
- **鍵は `storage` パーティションに置く**（KMU は後で調べる）。v1 は APPROTECT OFF（§8）なので、SWD で暗号文と鍵の両方が読める。この間の暗号化は「外付けの NAND を抜いて読む攻撃」に効く。KMU（鍵管理）に保護鍵を置けるか、使い方は未確認。

## §6 鍵と初期化（出荷時の書込み）

### §6.1 書込み

- **出荷前に MCUboot と初期アプリを書く**（SWD、1 回だけ）。以降の更新はスマホからの BLE DFU（確定。手順は [firmware.md §2.3](./firmware.md)）。PC が鍵を作って書き込む方式は採らない。
- 署名鍵は §7。出荷前に書くイメージは製品の署名鍵で署名する。

### §6.2 初回起動

- **鍵は初回起動時に本体が作る**（方針）。作るもの: OOB の秘密、保存データの鍵（AES-128）、デバイス ID。
- 置き場所は `storage` パーティション（確定。KMU は後で調べる）。
- 個体の状態（方針）:

```text
未初期化（秘密なし）   マイクを動かさない。録音しない
   ↓ 初回起動: 鍵を作る
ペアリング窓           広告はフラグのみ（§4）。LESC + OOB（§3）
   ↓ ペアリング成立 → 時刻を設定（TIME。[firmware.md §5.2](./firmware.md)）
初期化済み（ボンド済み）  録音を始める。Filter Accept List のみ接続可
```

- **ペアリング前の録音は保存しない**（確定）。初期化が終わるまでマイクを動かさない。録音の開始条件（ペアリングのみか、時刻設定まで含めるか）は未確定（末尾の「未確定」に記載）。
- 開発ビルド（Phase 0）は書込み直後から録音を始める（`PENDANT_AUTO_RECORD=y`）。製品ビルドでは上の状態機械に従う。

### §6.3 OOB の渡し方（未確定）

- 本体が初回起動時に鍵を作るので、OOB の秘密をスマホへどう渡すかが決まっていない。画面が無く、PC が書き込む方式（QR で渡す）も採らない。
- 論点: 出荷前の書込みの場で初回起動まで進めて QR を作る（出荷前の工程に載る）か、別の経路か。保存データの鍵をスマホが得る経路（LESC 成立後に暗号化リンクで渡すか、OOB と一緒に渡すか）。末尾の「未確定」に記載。

## §7 署名鍵と secure boot

- イメージは MCUboot が署名を検証する（ED25519）。署名付き OTA は確定（詳細は [firmware.md §2.2](./firmware.md)）。
- **署名鍵はメーカーの鍵 1 本で、全員のイメージに署名する**（確定）。**鍵はオフラインで保管する**（保管の方法は未確定）。購入者ごとに鍵を作らない。
- **NCS 同梱の開発用の鍵は開発専用。出荷するイメージには使わない。**
- MCUboot の署名検証（真正性）と APPROTECT（デバッガ）は別問題として扱う（§2）。
- 署名鍵の失効・更新（出荷後に鍵を替える手順）は未調査（末尾の「未確定」に記載）。

## §8 デバッグ保護（APPROTECT 等）

nRF54L15 には APPROTECT、SECUREAPPROTECT、ERASEPROTECT がある。

出典:
- https://docs.nordicsemi.com/r/bundle/nan_047/page/app/nan_production_programming/nrf54l/nrf54l_device_protection.html
- https://docs.nordicsemi.com/r/bundle/ps_nrf54l15/page/debug.html-access_port_protection

**v1 は APPROTECT / SECUREAPPROTECT / ERASEPROTECT をすべて OFF にする**（確定。設定していない。実機で SWD による書込み・メモリ読出しができていることがその証拠）。

- 理由: bring-up 中は SWD が最重要の復旧経路。電源経路と NAND を含む新規設計なので brick の確率が高い。Nordic は、APPROTECT と ERASEPROTECT の両方を有効にしたデバイスは適切なソフトウェアの仕組みなしでは復旧できないと警告している。
- 保存データは SWD の保護ではなく、§5 の暗号化で守る。
- SWD の service / recovery 用パッドは、将来 APPROTECT を有効にしても物理的に残す（パッドの仕様は [board.md](./board.md)）。unlock / recovery の方針が成り立ってからソフトウェア側で制限する。

段階導入（方針）:

```text
v1       SWD を全開
  ↓ ハードウェアが安定、OTA 試験済み、復旧試験済み
APPROTECT の評価
  ↓ secure boot と鍵の扱いが安定
SECUREAPPROTECT の評価
  ↓
ERASEPROTECT は本当に必要なときだけ
```

## §9 誤用・誤認対策

次の 3 つを入れる（確定）。

1. 筐体・箱・説明書に、常時録音であることを書く。
2. privacy latch を「録音の一時停止」として見せる。機構（スライドか磁気式か）は筐体と一緒に後で決める（[mechanical.md](./mechanical.md)、[product.md](./product.md)）。
3. 販売表示と規約は、日本と海外の法的確認を取る（専門家）。

入れないもの（確定）:
- 前面ボタンによる FW の一時停止。
- 録音インジケータ用の LED・音。追加の機構は作らない。
- 赤 / 黒の終端表示（Standard と Premium の両方に入れる）は **「録音中」とは謳わない**。通常時に赤が見えて「動作中」が周囲に伝わる。仕様は [terminal-indicator.md](./terminal-indicator.md)。

録音データの二次利用の制限は、アプリ側の規約で扱う（別）。
